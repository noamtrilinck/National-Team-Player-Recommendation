# UI/UX Redesign Round 3 (2026-08-30): Profile-relevance dependency chain (pre-implementation doc)

**Scope: presentation/explanation-selection layer only, as in rounds 1-2. Locked V2/F50 scoring
(Final Score, Global Rank, registry, Style/Emphasis definitions, weights) is untouched — verified
by regression at the end of this round, not by claim here.**

Point 8A of the round-3 request requires this chain to be documented, from real locked-architecture
data, **before** any explanation/chart-selection code changes. This file is that record.

## 1. The real dependency chain (as it exists in code today)

```
Selected Position (8-group locked scoring group, e.g. "Winger")
  -> Selected Style ("NoStyle"/"Control"/"Progression"/"Direct")            [meta.STYLE[style]]
  -> Selected Emphasis list (0-2 emphases valid for that position)          [meta.EMPHASIS[(pos,e)]]
       |
       v
  relevant Domains/Signals, derived ONLY from the same dicts scoring itself reads:
    - meta.STYLE[style]["core"] / ["supporting"] / ["core_receiving"] (Direct + receiving pos only)
    - meta.EMPHASIS[(position, emphasis)]["core"] / ["supporting"]
    - de.position_quality_weights(position)  (Position Quality's own weighted signals, no
      core/supporting split -- see below)
       |
       v  (precomputed at build time by data/build_dashboard_data_v2.py, NEVER re-derived by hand)
  data/relevant_signals.csv  (kind, role, position, key, signal_name, safe_name)
       |
       v
  src/explanation_engine_v2.py: relevant_signals_for(position, style, emphasis_list)
    -> set of (signal_name, safe_name) -- the candidate pool for explanation facts
       |
       v
  src/explanation_engine_v2.py: _collect_facts(...) joins signal_catalog.csv (domain, info_type)
    + signal_scores.parquet (global percentile, raw value, league-relative rank)
       |
       v
  explanation candidates (facts), one row per relevant, headline-tier (VOLUME/EXECUTION) Signal
       |
       v
  interestingness ranking + DOMAIN_INFO redundancy-group cap (existing round-2 logic, preserved)
       |
       v
  "Why He Stands Out" headline evidence  (ROUND 3: must now be PRIORITIZED by profile-relevance
  tier first, interestingness second -- see section 3)

  chart metrics (CHART_METRICS/PCT_METRICS, 27 raw match-level keys in build_dashboard_data.py)
    are a SEPARATE, non-overlapping identifier space from the 54 Signal names above -- there is
    no automatic join. Round 3 needs an explicit, disclosed CHART_METRIC -> Signal domain mapping
    (section 4) to let chart selection use the same relevance chain as explanations.
```

This confirms the chain the user asked to validate: **Style + Emphasis -> locked core/supporting
dicts -> relevant_signals.csv -> explanation candidates**, with zero manually invented
Style/Signal relationships — every relevant-signal fact traces back to `signal_meta.py`'s
`STYLE`/`EMPHASIS` dicts or `decomposed_engine.position_quality_weights()`, the exact same
functions the locked scoring engine itself calls.

## 2. The 5-tier profile-relevance hierarchy (data now available via `role`, added this round)

`relevant_signals.csv` (regenerated by `build_dashboard_data_v2.py`, see the `role` column added
in this round) gives, per (kind, role):

| kind              | role       | rows | meaning |
|-------------------|-----------|-----:|---------|
| emphasis          | core       |   47 | Tier 1 — Emphasis core signal |
| emphasis          | supporting |   21 | Tier 2 — Emphasis supporting signal |
| style             | core       |   72 | Tier 3 — Style core signal |
| style_receiving   | core       |    6 | Tier 3 — Direct-style receiving core (Direct + receiving positions only) |
| style             | supporting |   48 | Tier 4 — Style supporting signal |
| position_quality  | core       |  173 | Tier 5 — Position Quality only (generic, no core/supporting split in the locked architecture — Position Quality is a single weighted signal set, not itself tiered) |

A Signal that is relevant at multiple tiers (e.g. an Emphasis core signal that also happens to be a
Style core signal) is ranked at its **highest** (most specific) tier — Emphasis relevance always
outranks Style relevance, matching the user's explicit priority order in point 4 ("1. Selected
Emphasis relevance; 2. Selected Style relevance; 3. Secondary/supporting profile relevance;
4. General interestingness").

Within a tier, the existing round-2 `_interestingness()` scoring (extremeness + league-rank
quality) still decides ordering — this is exactly the "general interestingness decides between
similarly relevant candidates" rule from point 4, now applied inside each tier rather than across
the whole pool.

## 3. "Why He Fits [Emphasis]" — same-Style, different-Emphasis comparison

Reuses the existing `search_engine_v2.other_profiles()` **pattern** but needs a **different query**:
`other_profiles()` compares a player's own best Emphasis across *different Styles*; "Why He Fits"
needs the player's Final Score across *the same Style, different Emphases* (all real, existing
registry combos for that position+style — never averaged/synthetic, same rule as `other_profiles`).
This lets the section:
- state plainly when the selected Emphasis is the player's clear best for that Style (a real score
  gap vs the alternatives), and
- fall back to omitting the section (never forcing a comparison) when the gaps are small — per the
  explicit instruction "Do not force comparisons with alternative Emphases when there is no
  meaningful distinction."

The evidence used inside this section is scoped to Tier 1 (Emphasis core) first, Tier 2 second —
never Tier 3-5 — since the section's whole purpose is explaining the *Emphasis* fit specifically,
not the general profile.

## 4. Chart metric -> Signal domain mapping (manual, disclosed, needed because the identifier
   spaces don't overlap)

`CHART_METRICS`/`PCT_METRICS` (`data/build_dashboard_data.py`) are raw match-level stat keys (e.g.
`"touches"`, `"fouls_drawn"`) — a different, older export than the 54 Signal names in
`signal_catalog.csv` (e.g. `"Key Passes per90"`). To let chart selection follow the same
profile-relevance chain as explanations, each chart metric is mapped to the single locked Signal
domain it most directly measures — using the same 13 domains already defined in `DOMAIN_INFO`.
Where a chart metric has no defensible match to any locked domain, it is left **unmapped** rather
than force-fit — an unmapped metric can still be shown (general interestingness, Tier 4 in chart
terms), but can never outrank a domain-mapped, profile-relevant metric. This is the direct, disclosed
fix for the round-3 example bug ("Fouls Drawn" outranking core Ball Carrier metrics): `fouls_drawn`
has no genuine locked-domain match and is intentionally left unmapped.

| chart metric key         | mapped Signal domain            | domain group (DOMAIN_INFO) | confidence |
|---------------------------|----------------------------------|------------------------------|-----------|
| touches                   | Possession Involvement           | progression | exact-ish (Passes per90 is the domain's own Signal; touches is the closest raw proxy) |
| passes                    | Possession Involvement           | progression | exact-ish |
| accurate_passes           | Ball Progression -- Passing      | progression | exact-ish |
| passes_in_final_third     | Ball Progression -- Passing      | progression | exact (same Signal, "Passes in Final Third per90") |
| accurate_passes_pct       | Ball Progression -- Passing      | progression | exact (same Signal, "Accurate Passes %") |
| key_passes                | Chance Creation                  | creativity | exact (same Signal, "Key Passes per90") |

| assists                   | Chance Creation                  | creativity | close (end product of chance creation, no exact Signal) |
| total_crosses             | Wide Delivery / Crossing         | creativity | exact (same Signal, "Total Crosses per90") |
| accurate_crosses          | Wide Delivery / Crossing         | creativity | close ("Cross Accuracy %" is the %, this is a count) |

| shots_on_target            | Shooting                         | shooting | close ("Shot Accuracy %" is the closest existing Signal) |

This table is implemented as a plain dict in the chart-selection code (section 5/6 work, not yet
written) — not re-derived at runtime, and disclosed here exactly as built so any future audit can
check it against `signal_catalog.csv`'s 13 domains directly.

## 5. Chart tier priority (mirrors the 5-tier Signal hierarchy via the mapping above)

A chart metric's tier = the highest tier reached by ANY Signal in its mapped domain that is
relevant to the selected Style/Emphasis (using the same Tier 1-5 definitions as section 2). An
unmapped metric is always Tier 5-equivalent (general interestingness only) regardless of how
statistically discriminative it is — this is what stops a peripheral metric like Fouls Drawn from
ever outranking a core profile metric, per point 4's explicit requirement.

Within a tier, `charts.py`'s existing `differentiating_metrics()` percentile-spread ranking still
decides ordering (reused, not replaced) — general interestingness/discriminative value remains
the point-4 tier-4 tiebreaker, never the primary sort key.

## 6. Chart redundancy control (mirrors `DOMAIN_INFO`'s `group`, same 7 groups)

The first 3 charts draw from `DOMAIN_INFO`'s existing 7 redundancy groups
(`ball_winning`/`duels`/`progression`/`creativity`/`dribbling`/`shooting`/`retention`) — the SAME
grouping already used for explanation-fact redundancy (point 6's explicit ask: "similar to the
story-group logic already used for explanations"). At most one chart per group appears among the
first 3, so "Chart 1 = core domain, Chart 2 = key signal, Chart 3 = complementary dimension"
(point 5) is enforced structurally: the 3 charts are drawn from 3 different groups whenever at
least 3 groups have a relevant, mapped metric available, falling back to the next-best group only
when a Style+Emphasis genuinely doesn't span 3 groups (e.g. a very narrow Emphasis) — never forcing
an artificial 3rd dimension that isn't real.

## Implementation summary (points 1-6)

All implemented on top of the dependency chain above, nothing re-derived by hand:
- `explanation_engine_v2.py`: `_relevant_signal_tiers()` builds the 5-tier map straight from
  `relevant_signals.csv`'s `kind`/`role` columns; `build_explanation()`'s fact selection now sorts
  by `(tier, -interestingness)` instead of interestingness alone, so a Tier-1 (Emphasis-core) fact
  always outranks a more "interesting" but peripheral Tier-4/5 fact, while interestingness still
  breaks ties within a tier. Strength sentences gained a short, tier-derived lead-in
  (`_story_line()`: profile_driver/identity/combination/supporting_trait, general for Tier 5) laid
  over the existing raw-stat/league-rank evidence -- reduces repetition without inventing a
  causal claim, since the story type is a direct function of the fact's real tier.
- New `build_why_fits()`: "Why He Fits [Style/Emphasis]" scoped to Tier 1-2 evidence only, shown
  only when >=2 distinct-group facts clear a real bar (>=55th percentile) -- omitted, never
  forced, when there isn't genuine Emphasis-specific evidence (confirmed in the 12-player sample:
  omitted for Generic/NoStyle profiles and for single-domain Emphases like CB/Aerial where only
  one redundancy group has Tier-1/2 evidence). A "clear leader" intro line only appears when the
  selected Emphasis beats every real same-Style alternative combo
  (`search_engine_v2.emphasis_alternatives()`, new -- same never-synthetic rule as
  `other_profiles()`) by >=3 points; smaller/negative gaps suppress the leader framing rather than
  forcing a comparison, per the explicit instruction.
- `src/chart_relevance.py` (new): the disclosed `CHART_METRIC_DOMAIN` table (section 4) plus
  `select_priority_metrics()`, which re-sorts `differentiating_metrics()`'s already-discriminative-
  power-ordered pool by `(tier, original order)` and caps the first 3 picks to one per
  `DOMAIN_INFO` redundancy group. `views/recommendations.py`'s automatic chart batches now render
  3 independent single-metric range charts (no more Signal A / Signal B / A+B-combined pattern);
  the first batch is explicitly labeled Chart 1 -- Core Domain / Chart 2 -- Key Signal / Chart 3
  -- Complementary Dimension. The Custom Chart Builder is untouched (user-chosen chart type,
  including scatter/bubble, remains available there).
